# Development role boundaries

Apply the user's task, project instructions and actual client/server permissions
before using any role. Discover the selected Kodi version, source, owned workspace
and generation; never carry a historical target UUID into another installation.
Keep reusable workflow details in these skills rather than copying them into
every agent prompt. Available tools supply no task authorization or server grant.

- **Developer:** inspect the actual add-on manifest, reproduce the issue, edit only
  the approved source and run the release-matched static lane. For authorized Lab
  work follow [current contracts](current-contract.md): reviewed edit/import,
  exact-generation validation, preflight, admitted deployment, eligible launch and
  observation. Local files need an explicitly registered, synchronized source
  mirror before Lab can import them.
- **Runtime tester:** test the existing owned workspace. Do not edit source,
  create/import workspaces or repair infrastructure. Establish expected behavior,
  validate/preflight the same generation and deploy only when separately
  authorized and necessary. Use the validated manifest entry; fixed video smoke
  is not a generic Program-script launcher. Report blocked setup to its owner.
- **Inspector:** answer the requested diagnostic using only authorized target
  status, UI, inventory, bounded logs or images. Complete pagination before
  counting. Healthy status is not clean logs. Null UI fields are unknown. No
  navigation, deployment, execution, lifecycle or source edits.
- **Reviewer/repository manager:** preserve an existing project's independent
  review, artifact and publication policy. These roles are not automatically
  installed by the portable presets. Fixture adapters cannot qualify another
  project's source or release. Publication remains a separately authorized task.

Use only the tools needed for the question. Retain private receipts and warnings;
summarize source/workspace/generation, runtime/profile identity, actual observed
behavior, unresolved operations and next test. Static PASS, native readiness,
Bridge trust, deployment, dispatch, fresh code and feature acceptance are separate
claims. Reuse valid current evidence rather than reset, recopy or redeploy by
habit. Preserve the original request identity after an uncertain operation.

Inspection does not navigate. Lifecycle, navigation, settings, recovery and
promotion require separate explicit policy/task authority; default daily presets
do not add them. Never expand your own configuration or use direct RPC, shell,
another credential or a new workspace to bypass a refusal. Exclude production
targets from the ordinary development workflow.

Images require current screenshot authorization and actual image content reaching
an image-capable model. Capture metadata is not pixels. See [correlated capture
retrieval](mcp.md#action-observations-and-correlated-screenshots) and the current
contract's screenshot permissions; do not replay navigation to recover an image.
