# Current trusted managed Kodi agent workflow

Source checkpoint: Kodi Lab main `574eeee5b3dd444ab651cab3b73071714bd95ff6` (2026-11-14). Read the [server's tool and permissions matrix](https://github.com/kcook98765/kodi-lab/blob/main/docs/MCP-TOOLS-AND-PERMISSIONS.md), [unattended source installation](https://github.com/kcook98765/kodi-lab/blob/main/docs/MANAGED-ADDON-INSTALLATION.md), [agent project contracts](https://github.com/kcook98765/kodi-lab/blob/main/docs/AGENT-PROJECTS.md), and [Reset/Bridge recovery](https://github.com/kcook98765/kodi-lab/blob/main/docs/MANAGED-AGENT-RESET.md) for exact schemas and limits. This guide does not grant permissions. An installed server may differ: discover its authenticated tool schemas before runtime work.

## Select the environment

- **Trusted Managed Lab:** the administrator explicitly enables Full Development for the agent. This role covers approved, already installed disposable versions and agent-owned projects. It can admit autonomous Reset with independent Bridge preparation, subject to human priority, lifecycle, native identity, replay and resource guards. It does **not** install/acquire missing Kodi versions or grant external access.
- **Managed read-only/custom client:** require applicable client/Kodi policies, exact target grant, and specific permissions. `managed.versions`, `managed.lifecycle` and `managed.reset` are not synonyms. A read-only credential must not mutate.
- **External Production:** inspect scope and exact grant; screenshots and restricted navigation separately default Off on each Kodi. Select/Context are prohibited. No source deployment, lifecycle or agent-owned managed role.
- **External Development:** exact grant plus verified capability maxima; no assumption that managed launch or project authority transfers. Never widen the role to work around a missing tool.

## Preferred agent-owned source loop

1. `managed_status({})` to discover installed versions and exact profile/runtime identity. Select `matrix`, `nexus`, `omega` or `piers`; current Piers has qualified RC2, but existing profiles may remain pinned to RC1. Call `managed_start` with saved UUID/version only when authorized. Wait for `native_ready`, then independently check live Bridge readiness. Observe the one-running policy and human viewer/control holds.
2. `project_create` with saved request UUID and fresh add-on ID for a private inert Program/video-plugin starter; or `project_import` with a reviewed source ZIP, SHA-256 and provenance. Small inline intake allows at most 45 KiB compressed. For up to 4 MiB compressed (1,024 entries, 16 MiB expanded), stage reviewed chunks through `project_transfer` and then `project_import` using the retained transfer identity. This private ownership path needs no manual Web source registration/Current Kodi selection. Do not adopt another client's project.
3. `project_status` and `workspace_status` until owned workspace seed/capture is ready. `workspace_tree`/`workspace_read` verify actual generation/file hashes. For paginated reads use returned `next_line` until complete before full-file replacements. `workspace_edit` requires actual `expected_generation` and bounded payload. Keep returned generation; never increment locally.
4. `workspace_validate` (structural) then `workspace_deploy_preflight` with exact workspace/generation/target (no reservation). On a typed blocker, stop and follow only the supported recovery. Never treat static Toolkit validation as equivalent to Lab validation.
5. `workspace_deploy` on explicit managed target with a new saved request UUID, exact generation, and `deployment_mode: "direct"`. Retain tree/deployment receipts; `verified_existing` means current bytes verified, not fresh execution. If first-copy program/video enablement leaves the native Disabled add-ons question on screen, only an authorized same-profile `managed_stop` then `managed_start` using two separately saved UUIDs may clear it. Verify same profile and readiness again; do not automate bypassing consent.
6. `workspace_launch` with declared `extension_ordinal`, target, generation and another saved UUID. `development_launch` is a distinct declared-entry option. `workspace_execute` is a bounded fixed workflow, never arbitrary shell or Python. Inspect `inspect_ui_state`, `log_read`, and actual screenshot pixels if authorized. `remote_action` needs target control and defers to human input ownership. `addon_settings_set`/ `addon_settings_result` require explicit declared-setting authority (`development.settings.write`); a settings receipt does not itself relaunch or execute.
7. Iterate new validated generations; stop with `managed_stop` to retain Kodi state. `managed_release` releases eligible lifecycle ownership, not the Kodi process. For another version, stop current then start the next and independently deploy/verify its bytes.

## Autonomous clean Reset (only when the task authorizes destruction)

Read `managed_status` and save exact `profile_identity` for selected version. Pass `expected_profile`, version, saved UUID and optional `restart` (defaults false) to `managed_reset`. A stale binding refuses. Reset destroys Kodi writable profile/settings/add-ons but not owned project, workspace, Git, other versions or unrelated host state. It is never routine recovery. Replays use the **original parameters and UUID**, even after ambiguous responses. The returned `phase=complete` denotes replacement, not Bridge readiness. Inspect separate `bridge_preparation` checkpoint/receipt and live trust after Start. Resume using an expressly offered `resume_bridge_version` from original receipt only when original child is proven terminal and idle. Re-establish deployment evidence on replacement; older selected-session workflows may need administrator re-binding while stopped.

## Other supported but separate routes

Existing **registered source** workspaces use `development_source_list` and exact grants, `workspace_create`, `workspace_import_preview`/`workspace_import`, optional `workspace_source_scan`/`workspace_capture`, then validate/preflight/deploy. `managed_selection_preview`/`managed_select` do not grant access, start Kodi, or create a fresh source baseline.

`package_import`/`package_status` and `package_install`/`package_install_status` retain/deliver an original installable ZIP, **not** native ZIP GUI installation (Kodi Lab issue #305). Repository installation by ID cannot silently select a reviewed exact package and remains unresolved (issue #339). Use source deployment for agent-directed unattended work. `promotion_request` requests human review for eligible registered-source projects; never publishes and excludes agent-owned projects.

## Recovery and evidence

Hold the original UUID, exact arguments, profile, target, source/workspace/generation, current file hashes and operation receipt. A timeout, pending result or client output-schema error does not mean the server did nothing. Inspect receipt-first and never create a different request ID for unresolved work. Missing grants, human viewers, Bridge identity mismatch, reconciliation and capacity are not invitations to alter permissions, re-pair devices, call direct Kodi RPC, reset or bypass fences.

Report separately: source changed; static Toolkit validation; Lab structural validation; deployment preflight; deployed exact bytes; launch dispatched; native result observed; functional behavior verified. Limit claims to the tested Kodi release, exact profile/runtime, native host and workflow. Keep credentials, screenshots and logs private.
